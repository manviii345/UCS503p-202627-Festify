% ABSTRACT
% =========================================================
\section*{Abstract}
Fest committees at colleges rebuild registration forms, schedules, and communication
channels from scratch every year, relying on Google Forms, WhatsApp groups, static PDFs,
and manual reconciliation. \textbf{Festify} addresses this gap by delivering a reusable,
multitenant web platform: instead of building a new website, a college creates a fest
inside Festify, configures branding and events, and publishes it to students. The
project will design, build, and deploy a functional prototype within the semester,
centering on registration, secure QR-based check-in, a live schedule, an interactive
venue map, and an organizer dashboard -- with an optional, privacy-first crowd-density
layer built on top of, not required by, the core platform.

% =========================================================
% 1. INTRODUCTION & PROBLEM STATEMENT
% =========================================================
\section{Introduction \& Problem Statement}

Large, well-resourced events increasingly rely on dedicated event-management software,
yet most college fests are still coordinated through a patchwork of disconnected,
general-purpose tools. A typical fest committee opens a fresh Google Form for every
event, circulates a schedule as a static PDF that goes stale the moment a timing
changes, and answers "where is this happening?" through word of mouth. This is not a
failure of effort on the organizers' part -- it is a symptom of there being no
purpose-built, reusable system for a problem that recurs, almost identically, every
single year.

The resulting gap is felt on both sides of the fest. Students face a separate
registration form per event whose data never converges into one profile, schedules that
are outdated as soon as they are printed, difficulty navigating large or unfamiliar
venues, and entry passes scattered across email threads and screenshots that are easy to
lose or duplicate. Organizers, meanwhile, have no central registration view and must
reconcile headcounts by hand across dozens of spreadsheets; announcements are split
across WhatsApp groups, Instagram stories, and PA calls that frequently disagree with
one another; and crowd build-up at a stage or food court is only discovered once a
volunteer physically calls it in, rather than through live data. Because nothing from
one year's effort is designed to be reused, every committee starts over with new forms,
a new site (if any), and the same chaos the following year.

Festify proposes to close this gap with a single, reusable, multi-tenant web
application. Rather than shipping a fresh codebase per college, one deployment serves
every tenant: a college's data is fully isolated at the database and real-time layers,
but the underlying registration, scheduling, mapping, and dashboard logic is shared and
configured, not rebuilt. By treating fest management as a configuration problem instead
of a development problem, Festify turns a recurring annual cost into a one-time
engineering investment.

% =========================================================
% 2. OBJECTIVES
% =========================================================
\section{Objectives}

\textbf{Primary goal.} To design, develop, and deploy a functional, multi-tenant fest
management web platform -- covering registration, secure QR check-in, live scheduling,
and an organizer dashboard -- within the semester.

\textbf{Specific objectives:}
\begin{itemize}
    \item Implement a multi-tenant data model in which every table traces back to a
    \texttt{tenant\_id}, and every API request is authenticated and automatically
    scoped, so one college's organizers can never see or query another college's data.
    \item Build a student-facing registration flow with server-side, per-event capacity
    checks and a cryptographically signed QR pass issued on successful registration.
    \item Develop a live schedule and interactive venue map (zones, stages, stalls, and
    gates) backed by a PostgreSQL~+~PostGIS spatial data layer.
    \item Build an organizer dashboard exposing registration counts, event statistics,
    and real-time check-in numbers, updated via a Socket.IO real-time layer.
    \item Achieve a measurable performance target: a median \emph{Time-to-Check-In}
    (QR scan at the gate to dashboard update) of $\leq 2$ seconds during pilot testing.
    \item Design an optional, privacy-first crowd-density module that reports only
    aggregate, anonymized zone occupancy and can be disabled without affecting
    registration, passes, or schedules.
\end{itemize}

% 3. METHODOLOGY (SYSTEM ARCHITECTURE)
% =========================================================
\section{Methodology (System Architecture)}

This is an engineering course project, so the methodology emphasizes reusable,
multi-tenant architecture and workflow correctness over algorithmic novelty. The system
is built as a \emph{layered architecture}: each layer talks only to the layer
immediately above or below it, so any single layer can be swapped out later without
rewriting the rest of the system.

\subsection{Tech Stack}
The frontend is a \textbf{React~+~TypeScript Progressive Web App (PWA)} -- installable
to a home screen and capable of offline caching (via a Service Worker) for the
schedule, map, and QR pass, so the app remains usable even with unreliable venue
connectivity. The backend is a \textbf{Node.js~+~Express REST API}, exchanging JSON
over HTTPS. The primary data store is \textbf{PostgreSQL with the PostGIS extension},
chosen because fest data (tenants, events, registrations, venue zones) is highly
relational and PostGIS provides native spatial queries such as point-in-polygon.
 \textbf{Socket.IO} (built on WebSockets)
provides the real-time layer, using per-fest ``rooms'' so a broadcast to one college's
students never reaches another's. The system is containerized with \textbf{Docker} and
deployed through a \textbf{CI/CD} pipeline (test $\rightarrow$ build image
$\rightarrow$ deploy to staging), with a \textbf{CDN} serving static assets and map
tiles.

\subsection{Module Development}
The system decomposes into an authentication core plus functional modules built around
the database schema (Tenant, Fest, Event, User, Registration, Notification, Zone,
CrowdSnapshot). The \textbf{Auth \& RBAC module} issues signed JSON Web Tokens (JWT)
encoding the user's role (student / organizer / admin) and enforces which resources
each role may read or write, without the server needing to remember a session in
memory. The \textbf{Fest \& Event module} handles tenant-scoped creation and
configuration of fests, events, and venue zones -- with the \texttt{Zone} table using
single-table inheritance (a \texttt{type} discriminator distinguishing capacity-tracked
polygon zones from point landmarks like gates and washrooms) so one table cleanly
serves both the crowd module and the venue map. The \textbf{Registration \& Passes
module} performs server-side capacity checks and issues a signed QR token
(\texttt{payload~+~signature}, verifiable offline without a database round-trip). The
\textbf{Organizer Dashboard module} aggregates registration counts, event statistics,
and live check-in numbers. The optional \textbf{Crowd module} resolves opted-in student
locations to a venue zone via PostGIS point-in-polygon queries, then aggregates and
immediately discards individual pings -- \texttt{CrowdSnapshot} has no user-identifying
column at all, so the privacy guarantee is structural, not merely policy.

\subsection{Execution \& Integration}
The end-to-end workflow is: (1) a fest committee creates a fest and configures
branding, events, and venue zones; (2) a student joins the fest, browses events, and
registers, with capacity validated server-side; (3) the system issues a signed QR pass,
cached offline on the student's device; (4) volunteers scan the QR pass at the gate,
and check-in status propagates to the organizer dashboard in real time via Socket.IO.
All modules consume the same API and database, with the RBAC layer guaranteeing data
isolation between roles and the tenant layer guaranteeing isolation between colleges.

\subsection{Testing \& Validation}
Unit tests cover individual API endpoints and frontend components; integration tests
verify cross-module data flow (e.g., a newly created event correctly appears in the
student schedule and map); and scoped-query tests specifically target tenant isolation,
asserting that no query can return another tenant's rows. A \textbf{User Acceptance
Test} with a small pilot fest (25-50 student registrants, 5-10
volunteers/organizers) validates real-world usability, and performance is benchmarked
for Time-to-Check-In and concurrent dashboard load.

\subsection{Constraints \& Security}
Because the system handles registration and location data, security and privacy are
first-class concerns: passwords and tokens are never stored in plaintext, all traffic
is served over HTTPS, and every endpoint is role-gated through RBAC. Location
collection for the crowd module is strictly opt-in, gated behind explicit browser
permission, and only aggregate zone counts are ever persisted. To manage scope, the
semester deliverable is treated as a minimum viable product; the crowd-density module
is explicitly optional and designed to degrade gracefully (fail or be disabled without
breaking registration, passes, or schedules).

\section{Resources \& Budget}

\textbf{Human resources.} A three-member team with divided responsibilities across
frontend (React PWA, student- and organizer-facing UI), backend (REST API, database
schema, and multi-tenant isolation), and real-time infrastructure, testing \& deployment
(Socket.IO, Redis, Docker, CI/CD). Responsibilities overlap during the integration and
testing phases.


\textbf{Material resources.} Personal laptops; open-source frameworks (React,
Node.js/Express, PostgreSQL, PostGIS, Redis, Socket.IO); GitHub for version control;
and free-tier cloud services for hosting and managed PostgreSQL.

\textbf{Budget.} No external funding is required; all core resources are free,
open-source, or covered by university access. Optional costs -- a custom domain or
additional cloud capacity for the pilot -- are minimal and not required for the graded
prototype.

% =========================================================
% 6. RISK MANAGEMENT
% =========================================================
\section{Risk Management}

\begin{itemize}
    \item \textbf{Data privacy / consent:} Gate all location collection behind explicit
    browser permission; store aggregate zone counts only, never individual location
    history.
    \item \textbf{Tenant data leakage:} Enforce \texttt{tenant\_id} scoping at every
    query and cover it with automated tests before any feature ships.
    \item \textbf{Organizer adoption:} Keep the dashboard workflow minimal (create
    fest, add events, monitor, announce) and pilot with one small event before a full
    fest.
    \item \textbf{Offline reliability at the gate:} Rely on service-worker caching for
    QR passes and schedules so check-in does not depend on venue connectivity.
    \item \textbf{Scope creep:} Treat the crowd-density module as an optional add-on
    that can be deferred or disabled without affecting the core registration,
    scheduling, and check-in workflow.
    \item \textbf{Operational issues in pilot:} Use staging early and ensure the
    CI/CD pipeline produces repeatable deployments before the pilot event.
\end{itemize}
